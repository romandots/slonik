# slonk-drain

Автономный оркестратор, который **опустошает Kanban-доску проекта в Slonk**: вытягивает
задачи из входной колонки и проводит каждую по всему воркфлоу разработки до терминального
состояния (`Done`, `Cancelled` или `Blocked`).

Ключевая идея: **флоу не зашит в скилл — он обнаруживается в рантайме**. Состояния доски
читаются через `list_states`, а что именно делать на каждой стадии — определяется
конвенциями проекта (документация + доступные скиллы/команды). Поэтому один и тот же скилл
работает в проектах с разными досками и разными пайплайнами.

## Когда применять

Запускай, когда пользователь хочет массово, автономно довести задачи Slonk до завершения,
а не работает над одной конкретной задачей. Для одной задачи по номеру (`MPGU2-...`,
`SOF-...` и т.п.) обычно достаточно `git-flow` и прямой работы — `slonk-drain` нужен именно
для «прогнать всю доску».

## Перед запуском — обязательно

Это автономная операция, которая создаёт ветки, коммиты, PR и двигает карточки на общей
доске. Поэтому до начала прогона:

1. **Разреши проект и прочитай флоу** (см. `references/flow-discovery.md`). Без понимания
   стадий доски и проектных конвенций прогон начинать нельзя.
2. **Покажи план и подтверди scope.** Кратко сообщи пользователю:
   - какой проект и воркфлоу обнаружен (упорядоченная цепочка стадий);
   - сколько задач во входной колонке и их приоритеты;
   - сколько задач уже «в полёте» под нашим агентом (их продолжим);
   - предложи лимит (например, «возьму до N задач» или «все»), стратегию порядка
     (по приоритету → по давности) и режим (полный автоном vs. подтверждение перед
     каждым PR/мерджем).
   Дождись «поехали» прежде чем мутировать доску. Если пользователь явно сказал
   «полный автоном, не спрашивай» — не переспрашивай на каждой задаче, но сохраняй
   инварианты безопасности ниже.
3. **Зафиксируй стоп-условия:** входная колонка пуста; достигнут лимит задач; N задач подряд
   ушли в `Blocked` (вероятно, системная проблема — стоп и отчёт); пользователь прервал.

## Главный цикл (drain loop)

Обрабатывай задачи **по одной, полностью через флоу**, прежде чем брать следующую — так
доска всегда отражает реальное состояние, а прерывание прогона не оставляет полусделанного.

```
1. Собери очередь:
   а) сначала «свои» задачи в работе — claimed нашим агентом (operator) и стоящие
      в любой started-стадии: их надо ДОВЕСТИ, а не плодить новые (резюмируемость);
   б) затем задачи из входной колонки (unstarted / "To Do"),
      отсортированные: priority (urgent→high→medium→low→none), затем по давности.
2. Возьми следующую задачу из очереди.
   - Пропусти, если она claimed ДРУГИМ агентом (agent-claimed + чужой assignee) —
     это коллизия, не вмешивайся.
3. get_issue → прочитай заголовок, описание, метки, slonk:meta, историю при необходимости.
   Определи тип работы (feature / bug / refactor / chore) по меткам и тексту.
4. Если задача невалидна/устарела/дубликат → переходи к разделу «Отмена».
5. claim_issue(issue_id) — атомарно застолбить и войти в первую рабочую стадию.
   (Если уже claimed нами — пропусти claim, просто продолжай с текущей стадии.)
6. Веди задачу по стадиям started-группы в порядке sequence (см. «Прохождение по стадиям»).
   На каждой завершённой стадии — transition_issue в следующую.
   - Не можешь честно закрыть стадию → раздел «Блокировка». НЕ имитируй завершение.
7. Последняя рабочая стадия пройдена → transition_issue в completed-состояние (Done).
8. Короткий comment_issue с итогом (что сделано, ссылки на ветку/PR) — аудит-след.
9. Вернись к шагу 2, пока не сработает стоп-условие.
```

После цикла выдай **финальный отчёт**: таблица «задача → итог (Done/Blocked/Cancelled) →
ветка/PR → причина для Blocked/Cancelled», и что осталось во входной колонке.

## Прохождение по стадиям

slonk-drain отвечает за **механику доски** (claim, переходы, блок, done, комментарии), а
**саму разработку делегирует процессу, определённому в проекте** — не переизобретает его.

Стадии берутся из доски (`list_states`, группа `started`, порядок по `sequence`). Скилл
**проходит ровно те стадии, что есть**, и не придумывает новых: только `Development` —
весь содержательный цикл идёт на ней; расширенный пайплайн — по всем стадиям по порядку.

Источник действий на стадии — по убыванию приоритета:

1. **Скилл `dev-flow` проекта** (или процесс, описанный в `CLAUDE.md`). Если он есть — это
   канонический процесс разработки задачи с привлечением нужных субагентов. Делегируй ему
   проработку задачи, а slonk-drain синхронизирует доску переходами. **Это главный путь.**
2. **Субагент, соответствующий стадии.** Часто под колонку в проекте заведён субагент
   (напр. стадия тестирования ↔ тест-субагент, ревью ↔ ревью-субагент; бывают пары
   backend/frontend). Входя в стадию — **запусти соответствующего субагента**, передав ему
   задачу и контекст стадии. Сопоставление — по именам/описаниям в `.claude/agents/`.
3. **Слэш-команда по типу задачи** (`/feature`·`/bug`·`/refactor`) на стадии разработки.
4. **Профильный скилл** (`test-writer`, `doc-keeper`, `git-flow`).
5. **Фоллбэк:** выполнить работу напрямую по базовой эвристике из
   `references/stage-playbook.md`.

Независимо от того, кто делает работу, **критерий выхода со стадии оценивает slonk-drain**:
стадия двигается вперёд только при честно достигнутом результате; иначе — блок. Привязка
субагентов к стадиям, критерии выхода/блока, `link_git_ref` и этикет комментариев —
в `references/stage-playbook.md`. Прочитай его перед первым прогоном.

## Блокировка (вместо фейкового завершения)

Если стадию нельзя закрыть честно — **блокируй, а не имитируй**. Это главный инвариант
качества: лучше явный `Blocked` с причиной, чем «зелёная» карточка с битым кодом.

Блокируй (`block_issue(issue_id, reason=...)`), если:
- требования неоднозначны и нужно решение человека;
- нет доступа/секретов/окружения, которые не достать в рамках задачи;
- тесты падают, и причина — вне зоны задачи (или фикс рискует сломать чужое);
- этап упирается во внешнюю зависимость/чужую задачу.

В `reason` пиши конкретику: что именно заблокировало и что нужно от человека.
Незавершённую работу не оставляй в подвешенном виде: при блоке либо аккуратно
сохрани прогресс в ветке с пометкой, либо `release_issue`, если ничего полезного не сделано.

## Отмена

`Cancelled` — это суждение, поэтому **только с подтверждением пользователя** (кроме случая,
когда он заранее разрешил автоотмену дубликатов). Кандидаты: явные дубликаты, устаревшие
задачи, невалидные/пустые. Перед отменой — `comment_issue` с обоснованием.

## Инварианты безопасности (соблюдать всегда, даже в «полном автономе»)

- **Не имитировать результат.** Стадия двигается вперёд только по факту реального
  выполнения. Сомнение → блок.
- **Консервативность к необратимому.** Push, открытие/мердж PR, мердж в защищённые ветки,
  деплой, удаление данных, изменение прав/настроек — строго по правилам гита проекта
  (`git-flow` / документация / дефолты) и, если действие необратимо/затрагивает общий ресурс,
  с подтверждением. Никаких force-push и переписывания общей истории.
- **Не воевать с доской.** Чужие claimed-задачи не трогаем. Свой прогресс пишем через
  Slonk-инструменты (transition/comment/link), а не правкой meta вручную.
- **Изоляция изменений.** Каждая задача — своя ветка (по правилам гита проекта); не смешивать
  несколько задач в одном коммите/PR.
- **Останавливаться и докладывать.** Серия блоков подряд или повторяющаяся ошибка
  инструмента — это сигнал остановиться и показать отчёт, а не упорно долбить дальше.

## Справочные файлы

- `references/flow-discovery.md` — как разрешить проект и обнаружить воркфлоу (состояния
  доски, конвенции из CLAUDE.md/docs, доступные скиллы/команды, метки и slonk:meta).
- `references/stage-playbook.md` — детальный плейбук по стадиям: claim, ветки, коммиты,
  привязка git-ссылок, критерии выхода, шаблоны причин блокировки, этикет комментариев.
