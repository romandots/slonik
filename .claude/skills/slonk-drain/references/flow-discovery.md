# Flow discovery — разрешение проекта и обнаружение воркфлоу

Цель этого этапа — до начала прогона точно знать: **в каком проекте работаем**, **какая
упорядоченная цепочка стадий** на доске и **что физически делать на каждой стадии**.
Ничего не хардкодим — всё читаем из рантайма.

## 1. Разрешить проект

Порядок предпочтений:

1. Если пользователь назвал проект явно — используем его (передаём как `project` во все
   вызовы Slonk).
2. Иначе пытаемся вывести из контекста рабочей директории: имя репозитория, `CLAUDE.md`,
   `docs/SPEC.md`/`README.md`, идентификатор задач в коммитах (`MPGU2-`, `SOF-` и т.п.).
3. Иначе спрашиваем у Slonk: `who_am_i` (даёт `default_project` и `default_workspace`),
   при необходимости `list_workspaces` и `list_projects`, и показываем пользователю выбор,
   если кандидатов несколько.

Если уверенности нет — лучше уточнить у пользователя, чем опустошать не ту доску.

## 2. Прочитать стадии доски (канонический источник флоу)

`list_states(project)` возвращает состояния с полями `name`, `group`, `sequence`, `default`.
Группы Plane задают семантику, а `sequence` — порядок:

- `backlog` — необработанный бэклог. **Во вход drain не входит** (только `unstarted`),
  если пользователь явно не попросил включить бэклог.
- `unstarted` — **входная колонка** (обычно «To Do»). Отсюда берём задачи.
- `started` — рабочий пайплайн. Упорядочиваем по `sequence` — это и есть цепочка стадий
  разработки. Состояние с именем/смыслом «Blocked» из этой группы — **боковой терминал**,
  а не рядовой шаг: исключаем его из линейного прохода.
- `completed` — терминал успеха (обычно «Done»). Цель прогона.
- `cancelled` — терминал отмены.

Построй упорядоченный список рабочих стадий = `started` минус `Blocked`, отсортированный по
`sequence`. Пример из реального проекта SLONK:
`Analysis → Development → Security Review → Code Review → Testing → Documenting → Merging`.

Важно: **проекты разные**. Где-то будет только `Development`, где-то — расширенный пайплайн.
Проходи ровно те стадии, что есть. Не добавляй и не пропускай существующие.

## 3. Понять, что делать на каждой стадии (процесс проекта)

Имя стадии задаёт намерение, но **конкретный процесс разработки определяет проект**.
slonk-drain его не переизобретает, а делегирует. Источники, по убыванию приоритета:

1. **Скилл `dev-flow` проекта** (или процесс, описанный в `CLAUDE.md`). Если он есть — это
   канонический способ провести задачу через разработку, с указанием, какие субагенты
   привлекать на каких этапах. Делегируй проработку ему; slonk-drain лишь синхронизирует
   доску. Это главный путь — проверяй его наличие в первую очередь.
2. **Субагенты под стадии:** загляни в `.claude/agents/`. Часто на колонку заведён
   профильный субагент (тестирование, ревью, разработка; бывают пары backend/frontend).
   Сопоставь стадии доски с субагентами по их именам/описаниям — на этих стадиях запускаем
   именно их.
3. **Слэш-команды и профильные скиллы:** `.claude/commands/` и `.claude/skills/`. Типичные у
   этого пользователя: `/feature`·`/bug`·`/refactor` (разработка по типу задачи), `git-flow`
   (ветки/коммиты/мердж — **опционален**, есть не всегда), `test-writer` (тесты),
   `doc-keeper` (документация).
4. **Проектная документация как источник конвенций:** `CLAUDE.md`, `docs/CONVENTIONS.md`,
   `CONTRIBUTING.md`, `docs/ARCHITECTURE.md`, `README.md` — если явного `dev-flow` нет, здесь
   обычно описаны процесс и требования к тестам, докам, ревью, коммитам. **Правила гита**
   (имена веток, формат коммитов, целевая ветка, политика мерджа) при отсутствии скилла
   `git-flow` берём именно отсюда (подробнее — `stage-playbook.md`, «Работа с git»).
5. **Метки и `slonk:meta` задачи:** тип (feature/bug/refactor), приоритет, привязанные
   git-ссылки, предыдущий прогресс. Тип определяет, какую команду/субагента разработки звать.

Сформируй для прогона карту «стадия доски → процесс/субагент/команда», собранную из реальных
артефактов проекта (а не из памяти). Если проект не определяет ничего — переходи к базовой
эвристике из `references/stage-playbook.md`.

## 4. Снять стартовый срез доски

Перед планом собери цифры для подтверждения scope:

- `list_issues(project, state="<входная колонка>")` — что во входе, с приоритетами.
- `list_issues(project, label="agent-claimed")` или фильтр по нашему assignee — что уже
  «в полёте» под нашим агентом (их продолжаем) и что застолблено другими (пропускаем).
- При необходимости `list_states` ещё раз, чтобы показать пользователю обнаруженную цепочку.

Эти данные идут в план scope (см. `SKILL.md`, «Перед запуском»).
