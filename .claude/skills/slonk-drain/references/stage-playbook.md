# Stage playbook — как проводить задачу по стадиям

Детальные правила для шага 6 главного цикла. Общий принцип: на каждой стадии есть
**действие** и **критерий выхода**; стадия двигается вперёд (`transition_issue`) только когда
критерий честно выполнен. Не выполнен и не выполним — `block_issue`.

## Вход в работу: claim

- `claim_issue(issue_id)` — атомарно: назначает задачу на нашего агента, ставит метку
  `agent-claimed`, переводит в стартовую стадию роли. Это защита от коллизий на общей доске.
- Если `claim_issue` вернул конфликт (успел другой агент) — не настаиваем, берём следующую.
- Если задача уже claimed нами и стоит в started — claim не повторяем, продолжаем с текущей
  стадии (резюмируемость прерванного прогона).
- `target_state` у `claim_issue` используем, только если нужно войти в конкретную стадию,
  отличную от роли-дефолта.

## Работа с git: откуда брать правила

Ветки, формат коммитов и стратегию мерджа определяй по **источнику правил гита проекта**,
по убыванию приоритета:

1. **Скилл `git-flow`**, если он есть в проекте — используй его (он сам определит неймспейс,
   формат имени ветки и стратегию мерджа, в т.ч. по пути рабочей директории).
2. **Правила гита в документации**, если `git-flow` недоступен — ищи их в `CLAUDE.md`,
   `docs/CONVENTIONS.md`, `CONTRIBUTING.md`, `README.md`: соглашения об именах веток, формат
   коммитов (например, Conventional Commits), целевая ветка, политика PR/мерджа. Следуй им.
3. **Разумные дефолты**, если нигде не описано: ветка под задачу с идентификатором в имени
   (напр. `feature/<ID>-<slug>`), осмысленные атомарные коммиты, мердж в основную ветку
   разработки (обычно `develop`). Дефолты — последний выбор, не подменяй ими явные конвенции.

Имя ветки в любом случае должно содержать идентификатор задачи — это связывает код с
карточкой. После создания ветки/PR привязывай их к задаче: `link_git_ref(issue_id, repo_url,
branch=..., pr_url=..., commit=...)` — даёт прослеживаемость код ↔ карточка и поиск задачи по
git-ссылке (`find_issues_by_git_ref`). Идемпотентно.

## Делегирование: dev-flow и субагенты под стадии

Прежде чем делать работу руками, проверь, что проект уже определяет процесс (см.
`flow-discovery.md`, раздел 3):

- **Есть `dev-flow`** → делегируй ему всю проработку задачи; slonk-drain только двигает
  карточку по стадиям по мере готовности и блокирует/завершает по его результату.
- **Есть субагент под стадию** → входя в стадию, запусти соответствующего субагента (через
  механизм субагентов Claude Code / Task), передав: идентификатор и текст задачи, тип
  (feature/bug/refactor), имя текущей стадии и ожидаемый результат стадии. Дождись итога,
  оцени критерий выхода, затем переходи дальше или блокируй.
- **Есть слэш-команда/скилл** → используй её (`/feature`·`/bug`·`/refactor`, `test-writer`,
  `doc-keeper`, `git-flow`).

Сопоставление стадии и субагента — по именам/описаниям в `.claude/agents/` (напр. стадия с
«test» в имени ↔ тест-субагент, «review» ↔ ревью-субагент). Если соответствия нет — спускайся
к фоллбэку ниже. Решение «стадия закрыта / блок» всегда остаётся за slonk-drain, кем бы ни
выполнялась работа.

## Базовая эвристика по стадиям (фоллбэк, если проект ничего не определяет)

Применяй, только когда нет ни `dev-flow`, ни субагентов, ни команд/скиллов под стадию.
Адаптируй под реальные имена стадий из `list_states`.

**Analysis / Анализ.** Прочитай issue, описание, метки, связанный код. Составь короткий план.
Выход: план ясен, объём понятен. Блок: требования неоднозначны, нужен выбор/решение человека.

**Development / Разработка.** Реализуй изменение в ветке задачи по конвенциям проекта.
Выход: изменение реализовано, проект собирается/стартует. Блок: нужен недоступный
ресурс, или задача упирается в чужую незавершённую работу.

**Security Review.** Просмотри диффы на секреты в коде, инъекции, небезопасные доступы,
утечки. Выход: явных проблем нет либо они устранены. Блок: проблема требует
архитектурного решения.

**Code Review.** Самопроверка: соответствие конвенциям, линтеры, статанализ (например,
PHPStan для PHP-проектов). Выход: проверки чистые. Блок: ошибки, фикс которых выходит за
рамки задачи.

**Testing / Тесты.** Напиши/обнови тесты и **запусти** их. Зелёные тесты — обязательное
условие выхода. Блок: тесты падают по причине вне зоны задачи, или окружение недоступно.

**Documenting / Доки.** Актуализируй документацию под изменения. Выход: доки соответствуют
коду. Блок (редко): нужна информация, которой нет.

**Merging / Мердж.** Финализируй по правилам гита проекта (см. «Работа с git» выше:
`git-flow` → правила в документации → дефолты): коммит в принятом формате и вливание в
целевую ветку (обычно `develop`). **Необратимые/общие действия** (push, открытие/мердж PR,
мердж в защищённые ветки, деплой) — по конвенциям проекта и, если действие необратимо или
затрагивает общий ресурс, с подтверждением пользователя (если он не разрешил полный автоном).
Никаких force-push и переписывания общей истории. Выход: изменения влиты согласно флоу.

## Переход к терминалу

- Все рабочие стадии пройдены → `transition_issue(issue_id, state="<completed>", comment=...)`
  (Done). В комментарии — краткий итог и ссылки на ветку/PR.
- Невыполнимо честно → `block_issue` (см. ниже). Невалидно/дубликат → отмена (с подтверждением).

## Блокировка — шаблоны причин

`block_issue(issue_id, reason=...)` ставит `Blocked` + метку `agent-blocked` + комментарий.
Причина должна быть **конкретной и действенной для человека**. Примеры формулировок:

- «Неоднозначные требования: не указано <что>. Нужно решение: <варианты>.»
- «Нет доступа к <ресурс/секрет/окружение>, без него реализовать/проверить нельзя.»
- «Тесты <какие> падают из-за <причина вне зоны задачи>; фикс затронет <что> — нужно решение.»
- «Зависит от незакрытой задачи <id/описание>.»

При блоке сохрани полезный прогресс в ветке (с пометкой в комментарии), либо `release_issue`,
если ничего ценного не сделано и задача должна вернуться во вход чистой.

## Отмена — критерии

Только с подтверждением пользователя (или при заранее данном разрешении на автоотмену
дубликатов). Кандидаты: явный дубликат существующей задачи; устаревшая/неактуальная; пустая
или невалидная. Перед `transition_issue(... state="<cancelled>")` — `comment_issue` с
обоснованием, чтобы остался след решения.

## Этикет комментариев (аудит-след)

`comment_issue` (он сам префиксует идентичностью агента) — в ключевых точках, кратко:
- при claim — что взяли в работу и план в двух строках;
- при значимых переходах — что сделано на стадии (особенно перед Done/Blocked);
- при блоке/отмене — причина (дублирует reason человекочитаемо).

Не засоряй: 1–2 строки на событие. Цель — чтобы человек, открыв карточку, понял историю без
чтения всего диффа. Для дедупликации повторных комментариев при ретраях используй
`client_dedup_key`.
